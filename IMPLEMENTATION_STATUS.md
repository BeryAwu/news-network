# Implementation Status

This file records the current implementation and its evidence. Product requirements and planned capabilities remain in `docs/`; a requirement is not considered delivered unless this status or a verification record says so.

## Current application

- Next.js App Router, TypeScript, PostgreSQL, and Prisma modular monolith with authenticated dashboard and host-resolved public media/article routes.
- Local private PostgreSQL 18 cluster is configured at `127.0.0.1:5433`; use `scripts/start-local.ps1` to start/reuse it and run the local app at `http://localhost:3000/login`.
- Linux dev setup (current): Postgres 17 runs as container `nnms-postgres` on the VPS (bound to the VPS's 127.0.0.1:55432, 256 MB limit, volume `nnms-pgdata`; other apps there are untouched). Laptop reaches it through `scripts/db-tunnel.sh` (SSH tunnel on localhost:5432), so `DATABASE_URL` stays `localhost:5432`. Open the tunnel before `npm run dev`. Smoke-tested on this DB: login, media/domain verify/category/brief, real OpenRouter draft, manual edit, approve, inline publish, public render on the verified host (404 on an unknown host), and a real Cloudinary upload (1 tiny PNG, `nnms/media/.../library/`, left in the Cloudinary account). Test rows were truncated afterwards; DB holds only the seeded owner and writing skill.
- Local owner account is `owner@newsroom.local`. The password and all API/database secrets remain in ignored local files; never copy them into documentation or Git.
- The local database contains test records made during workflow debugging. Do not treat them as real newsroom content or a clean empty database. Reset only after confirming local test data is disposable.

## Implemented capabilities

- Authentication with signed HTTP-only sessions, server-side role/media-scope checks, same-origin mutation checks, audit records, and in-memory rate limits for login, AI actions, source ingestion, uploads, and publishing.
- Media profiles, categories, domains, role/user management, and host-based tenant resolution. Domain verification is an admin record of an external ownership check; the app does not perform DNS verification.
- Source briefs with optional narrative and optional references. A topic alone can be used to request an AI-authored draft; supplied facts/references remain evidence inputs and unsupported specifics must not be presented as verified.
- Bounded public HTTP(S) reference retrieval with DNS/public-IP validation, pinned requests, redirect checks, robots policy, size/time/content bounds, and per-reference status.
- OpenRouter integration with structured-output validation, Qwen3 235B configured as the local default, Qwen3 32B as an optional lower-cost model, and a development-only deterministic test adapter. Generation is versioned per media; invalid/unsupported source-fact citations are rejected.
- Editorial workflow: manual edit, AI revision, approval/rejection/needs-changes, individual and bulk review, immutable evidence snapshots, version history, restore, and compare-and-set protections for concurrent writes. Repeated restore of identical content does not create duplicate versions.
- Mandatory Cloudinary asset handling using the official server-side SDK, upload validation, provenance/license metadata, media scope checks, and publication-time featured-image snapshots. No real image upload has been completed yet.
- Per-domain publication targets with immutable approved-version snapshots, attempt history, idempotency, state guards, inline immediate publication, and optional BullMQ/Redis worker support. Scheduled execution and worker retry have not been verified locally because Redis is unavailable.
- Dashboard, monitoring, integrations/setup surfaces, responsive navigation, paged list APIs, editorial queue pagination, CSP/security headers, and safe generic server errors.
- Writing skills: per-media on/off guidance blocks that inject a fixed narrative style into AI drafting and revision prompts (seeded skill `humas-instansi`, derived from public-service/police press-release style). Skill state lives in `WritingSkill`/`MediaWritingSkill` tables, is audited, and is toggleable both from the media edit card and from a "Gaya penulisan AI" section on every editorial article card.
- AI readiness is reported honestly in the editorial UI: the revision section states whether a real provider or the deterministic test adapter is active, generation is blocked while the test adapter is on, and a revision that fails keeps the previous article version untouched while returning an actionable 502 message instead of a generic internal error.
- Public news site (host-resolved, same codebase): home with featured lead, search, pagination, category pages (`/kategori/[slug]`), article pages with SEO/OpenGraph/JSON-LD, related articles, evidence section, AI-assistance notice, per-host `sitemap.xml`, `rss.xml`, `robots.txt`, and per-media theme (primary colour, tagline, Cloudinary logo) edited from the media card. Unknown or unverified hosts get 404. Verified in Chromium on a pilot media (`pilot.localhost`) at desktop and mobile widths.
- Unpublish: `POST /api/publish {action:"unpublish"}` cancels live targets, returns the article to APPROVED so it can be edited, re-reviewed and republished; button in the Publishing history table. Verified: article disappears from the site (direct URL 404) and returns after republish.
- Background AI drafting: `generate` returns 202 immediately, creates PENDING `AiGenerationRun` rows and runs them via Next `after()` with concurrency 3 (`lib/generation.ts`); `GET /api/generation` feeds a live progress list in the editorial panel; duplicate clicks do not duplicate runs; runs pending over 15 minutes are marked INTERRUPTED. This is in-process (no Redis): a server restart mid-run loses that run, it does not resume.
- `APP_MODE` (`proxy.ts`): `public` serves only site routes, `admin` only the ADMIN_BASE_URL host, `all` (default) both, so the dashboard and the public sites can be deployed as separate processes from one repo.
- Server backup: daily `pg_dump` of the `nnms-postgres` container to `/var/backups/nnms` (7 days, cron `/etc/cron.d/nnms-backup`) on the same VPS disk; no off-server copy yet.

Verified by unit tests (report builders, author token, proxy); screens were written without running a browser (owner laptop is weak) and are tested on the deployed server.
- AI sources (Koneksi layanan, no migration; rows in `IntegrationSetting`): two kinds. **OpenRouter** pool (`ai.key.*`, model `ai.model`, per-key `ai.keymodel.*`): many keys, bulk paste, round-robin per request (`ai.keyIndex`, advanced only by real AI calls), always sent to `openrouter.ai`; "Import dari /models" also stores the free text-only models (`ai.freeModels`) that are tried automatically when the chosen model is slow, busy, or returns an empty/invalid answer. **Paid providers** (`ai.paid.<id>`, encrypted `{apiKey, baseUrl, model}`): OpenAI-compatible, one key each, model typed by the owner, tested on add, never rotated into OpenRouter free models. `ai.active` (`openrouter` or `paid:<id>`) picks the source tried first; the other sources are backups and the server key is last. Per request: up to 2 OpenRouter keys, 60 s per model, 150 s and 10 models per key, `max_tokens` 8000 (reasoning models need the headroom), `data_collection: "deny"` kept for every OpenRouter call. Each run log (`AiGenerationRun.errorMessage`) lists every model tried and why it was skipped.
- Owner-managed AI key (migration `20261116_integration_setting`): Koneksi layanan has a "Kunci AI (OpenRouter)" card for the OWNER. The key (and optional model) is tested against OpenRouter first (`/auth/key` plus one tiny completion), saved only when it works, stored AES-256-GCM encrypted with a key derived from SESSION_SECRET (`lib/secrets.ts`, table `IntegrationSetting`), and read back to confirm. `aiConfiguration()` is now async and reads the dashboard key fresh on every call, so the next AI request uses it with no restart; it wins over the server env, and the key is never sent to a custom base URL. API: `GET/PUT/POST(check)/DELETE /api/settings/ai` (OWNER only, rate limited, audited without the secret). Failed AI runs now say why in plain words (credit spent, key rejected, rate limit) via `plainAiFailure`. If SESSION_SECRET is rotated the saved key becomes unreadable and the card asks for it again. Several keys with automatic failover (migration `20261117_ai_key_pool`): the card is now a list; each key is its own encrypted row with a position. `generateDraft` tries keys in order, then the server env key last. 402 rests a key for 6 h, 429 for 5 min, 401/403 marks it rejected (owner must replace it); other errors do not rotate. Rest and rejection are saved, shown on the card, and can be reset. Max 8 keys; AI settings are OWNER-only (nav and page). Pustaka gambar page removed (images are uploaded inside the berita wizard). Ten public designs (`lib/site-themes.ts`, `components/site/themes/*`, `app/css/themes/*`) chosen per media in the media form; each media shows a logo mark and its own tab icon (`/site-icon`); the dashboard has its own Newsroom logo and tab icon. New media are auto-granted to non-admin team members. Per-berita reports: the Laporan page lists published berita for the period with Word, PDF and Excel (links) downloads per berita.
